1. Introduction et contexte métier

Ce projet a pour objectif la conception, la modélisation et l'implémentation d'un Data Lake permettant l'intégration et la préparation de données hétérogènes, dans le cadre du cours Warehousing, Data Lakes & Polystores du Master 2 DS4SC de l'Université de Blois.

1.1 Cas d'usage

Le client fictif est l'agence immobilière Clé en Main Immo, qui souhaite disposer d'un observatoire automatisé pour répondre à cinq besoins métier :

  • B1 — Argumentaire de prix en temps réel pour un bien visité
  • B2 — Score de potentiel pour l'implantation d'une 6e agence
  • B3 — Recherche de logement autour du lieu de travail d'un couple
  • B4 — Indicateur de tendance du marché sur 5 ans
  • B5 — Détection de zones sous-évaluées mais bien équipées

1.2 Périmètre géographique

Quatre régions françaises : Île-de-France, Bretagne, Occitanie et Auvergne-Rhône-Alpes, soit 37 départements. Période couverte : 2021–2025.

2. Architecture du Data Lake

2.1 Choix de l'architecture médaillon

Nous avons retenu une architecture à trois zones (medallion architecture) : Bronze, Silver, Gold. Ce choix permet :

  • de conserver les données brutes intactes (auditabilité)
  • de séparer clairement les étapes de nettoyage de celles d'analyse
  • de rejouer une couche sans tout réingérer

2.2 Vue d'ensemble

ZoneFormatContenuVolume
BronzeJSON / CSV brutDonnées sources téléchargées~4,6 Go
SilverParquet + PostgreSQLDonnées nettoyées~2,4 M lignes
GoldPostgreSQL4 tables analytiques~2,3 M lignes

2.3 Justification des formats de stockage

Bronze — JSON et CSV : Les données sont conservées dans leur format d'origine (fichiers tabulaires DVF avec séparateur |, JSON Overpass, JSON API Melodi INSEE). Aucune transformation n'est appliquée à ce stade, garantissant la traçabilité.

Silver — Parquet : Le format Parquet a été retenu pour sa compression colonaire (division par ~5 du volume par rapport au CSV), son typage explicite et son interopérabilité avec pandas. Chaque source produit un fichier Parquet unique.

Gold — PostgreSQL : Les quatre tables analytiques sont stockées dans PostgreSQL pour permettre des requêtes SQL complexes (fenêtres, agrégats, jointures multi-sources), l'exposition via une connexion réseau unique et le déploiement sur la plateforme universitaire Portainer.

3. Pipeline ETL — de Bronze à Gold

3.1 Étapes du pipeline

  1. Ingestion Bronze — téléchargement des sources dans leur format d'origine (src/dvf/main.py, src/osm/main.py, src/insee/main.py)
  2. Profilage Bronze — diagnostic de qualité sur chaque source (profiling.py par module)
  3. Nettoyage Silver — transformation et validation (silver.py par module + src/communes/silver.py)
  4. Chargement Silver → PostgreSQL — via src/charger_silver_postgres.py
  5. Construction Gold — src/gold/modele_conceptuel.py
  6. Contrôle Gold — src/gold/controle.py

3.2 Fédération de données (Polystore)

Les requêtes Gold réalisent la jointure croisée entre les quatre sources hétérogènes. La requête B3, par exemple, associe en une seule requête SQL :

  • les transactions DVF (prix, surface)
  • les POI OSM (transport, équipements, géolocalisation)
  • les profils INSEE (revenus, population)
  • le référentiel communal (noms, régions)

7. Analyses métier B1 à B5

7.1 B1 — Argumentaire de prix

Situation : un négociateur doit défendre le prix d'un bien pendant une visite.

La requête calcule la médiane des médianes annuelles du prix au m² dans la commune (années ≥ 10 ventes). Elle retourne : médiane, moyenne, Q1, Q3, min, max.

Exemple : Appartement Paris 11e proposé à 5 385 €/m², médiane de marché à 9 812 €/m² → 45,1 % sous le marché.

7.2 B2 — Score d'implantation agence

Score composite (10 meilleures communes par région) :

Score = 0,40 × dynamique_prix + 0,30 × activité_ventes + 0,30 × équipements

Les trois composantes utilisent CUME_DIST() pour normaliser les valeurs sur [0, 1] dans leur région, rendant les 4 régions comparables.

7.3 B3 — Recherche logement autour du travail

La requête croise DVF (prix biens comparables), OSM (accessibilité) et INSEE (profil). Le ratio_prix_revenu_annuel mesure l'effort financier : un ratio de 8 = 8 années de salaire brut.

7.4 B4 — Tendance du marché

Utilise LAG() et generate_series() pour une série temporelle complète 2021–2025. Verdict : hausse / stable / baisse / non_concluante (±3 %).

Exemple : Lyon Appartement : baisse (−12,5 % sur 5 ans).

7.5 B5 — Zones sous-évaluées

Filtre les communes : prix médian < seuil régional (90 %), score équipements > 60/100, revenu médian positif. Ce dernier critère écarte les zones simplement pauvres.

8. Déploiement

8.1 Image Docker

L'image est publiée sur Docker Hub : rayanhcm0/datalake-immo:latest. Elle est compilée en linux/amd64 depuis Apple Silicon avec docker buildx.

docker run --env-file .env -p 8888:8888 rayanhcm0/datalake-immo:latest

Accès au notebook : http://localhost:8888 — mot de passe : cleenmain2025

8.2 Portainer — plateforme universitaire

Le container est déployé sur la plateforme Docker de l'université. La connexion PostgreSQL est configurée via la variable d'environnement DATABASE_URL. Les tables Silver et Gold sont déjà peuplées ; le notebook s'exécute sans ré-ingestion.

9. Conclusion

Ce projet met en œuvre une architecture Data Lake complète :

  • 3 sources hétérogènes intégrées (fichiers plats, API JSON, données spatiales)
  • Architecture médaillon Bronze / Silver / Gold avec justification des formats
  • 6 types d'actions correctives documentées et quantifiées
  • Fédération polystore réalisée en SQL sur 4 tables issues de sources distinctes
  • 5 analyses métier complexes paramétrables et opérationnelles
  • Déploiement Docker sur la plateforme universitaire

L'ensemble du pipeline est reproductible depuis les scripts fournis. Le notebook analyse_immo.ipynb constitue le démonstrateur interactif final.
